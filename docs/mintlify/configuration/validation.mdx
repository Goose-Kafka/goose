# Schema Validation

| Env Var | Default | Description |
|---------|---------|-------------|
| `SCHEMA_VALIDATION_ENABLED` | `false` | Enable validation |
| `SCHEMA_VALIDATION_CEL_EXPRESSION` | _(empty)_ | Semicolon-separated CEL expressions (all must pass) |
| `SCHEMA_VALIDATION_ON_FAILURE` | `dlq` | `dlq`, `ignore`, or `drop` |

## How It Works

After schema parsing (proto→JSON or JSON passthrough), goose evaluates each CEL expression. All must return `true` for the message to be valid.

```
Message JSON
  → validate expression 1: has(message.order_id) && message.order_id != ""
  → validate expression 2: message.amount > 0
  → validate expression 3: message.status in ["created","pending","shipped"]

All pass → proceed to filter → worker → sink
Any fail → DLQ (or ignore/drop based on config)
```

## Examples

```properties
# Single expression
SCHEMA_VALIDATION_CEL_EXPRESSION=has(message.order_id) && message.order_id != ""

# Multiple expressions (semicolon-separated)
SCHEMA_VALIDATION_CEL_EXPRESSION=has(message.order_id) && message.order_id != ""; message.amount > 0; message.status in ["created","pending","shipped"]

# Nested fields
SCHEMA_VALIDATION_CEL_EXPRESSION=has(message.payment.amount) && message.payment.amount > 0
```

## Validation vs Filtering

| | Validation | Filtering |
|---|---|---|
| Purpose | "Is this message well-formed?" | "Do I care about this message?" |
| On failure | DLQ or drop | Drop (offset advances) |
| Runs | Before filtering | After validation |
